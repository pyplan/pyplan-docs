# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repository is

`pyplan-docs` is the **public documentation site** for Pyplan (a no-code/low-code Planning & Analytics platform), built with **Docusaurus 3** + React 19 + TypeScript. It is content, not product code — the actual product lives in the sibling repos that are also mounted as working directories (`pyplan-ui`, `pyplan-engine`, `pyplan-ai`, `pyplan-api`). Changes here almost always mean editing Markdown under `docs/`, not application logic.

## Commands

```bash
npm install          # install deps (Node >= 20; .node-version pins 24 for local dev, CI uses 20)
npm start            # dev server with live reload at http://localhost:3333
npm run build        # production build into build/ — this is the CI gate (see below)
npm run serve        # serve the built site at :3333
npm run typecheck    # tsc, no emit
npm run clear        # clear the .docusaurus cache (use when the dev server behaves oddly)
```

There is no test suite. **`npm run build` is the only validation gate** — every PR runs it (`.github/workflows/test-build.yml`) and a merge to `main` rebuilds and deploys (`deploy.yml`). Before considering content changes done, run `npm run build` to catch broken links and MDX parse errors.

## Content architecture

- **Docs are served at the site root, not under `/docs/`** — `routeBasePath: '/'` in `docusaurus.config.ts`. A file at `docs/user-guide/applications.md` is reachable at `/user-guide/applications`. Internal links in Markdown should use these root-relative URLs (e.g. `/user-guide/access-to-pyplan`), as `intro.md` does.
- **The sidebar is fully autogenerated** (`sidebars.ts` → `{type: 'autogenerated', dirName: '.'}`). You do not hand-edit a sidebar list. Ordering and grouping come from:
  - `sidebar_position` in each file's frontmatter, and
  - `_category_.json` in each directory (sets the section `label`, `position`, and the generated-index landing page `description`).
  When adding a doc, set its `sidebar_position`; when adding a section folder, add a `_category_.json`.
- Top-level sections under `docs/`: `user-guide/`, `tutorials/`, `technical-docs/`, `faq/`, plus `intro.md` (the `slug: /` landing page).

## Conventions

- **Frontmatter**: every doc starts with a YAML block — at minimum `title` and `sidebar_position`. `intro.md` additionally uses `slug: /`.
- **Images are co-located per section.** Each content folder has its own `img/` subfolder and docs reference it with a **relative** path: `![alt](./img/foo.png)`. This differs from site-chrome assets (logo, favicon, social card) which live in `static/img/` and are referenced **absolutely** as `/img/foo.png`. Follow the relative-`./img/` pattern for documentation screenshots.
- `onBrokenLinks` and broken-image hooks are set to `'warn'`, so a bad link will **not** fail the build — watch the `npm run build` output for warnings rather than assuming success means all links resolve.

## Authoring documentation (style & workflow)

These conventions come from the project's docs-writer agent (`.github/agents/pyplan-docs-writer.agent.md`) and apply whenever creating or updating articles. **Before writing, read the existing file (for updates) or neighboring files in the same section (for new articles)** to match the established tone and structure.

**Language**

- **Articles are always written in English**, regardless of the conversation language. The user may provide source content in any language — translate and adapt naturally into idiomatic English; never translate literally.
- **Reply to the user in their own language** (e.g. Spanish in, Spanish out) even though the docs themselves stay in English.

**Voice & tone**

- Use **first-person plural** — "we", "our", "us". Never address the reader as "you should". E.g. *"In this section we describe…"*, *"To continue, we select the **Save** option."*
- Professional, accessible, direct, unambiguous. Introduce technical terms in **bold** on first use, and bold the names of UI elements (menus, buttons, dialogs).

**Article structure**

- YAML frontmatter (`title`, `sidebar_position`) → H1 title → a short intro paragraph explaining *what* the feature is → H2/H3 sections.
- Step-by-step procedures as **numbered lists**, with UI element names in bold.
- Place each screenshot **immediately after** the step or section it illustrates.
- Use Docusaurus admonitions (`:::info`, `:::tip`, `:::warning`) for important notes.
- End long/tutorial-style articles with a summary section.

**Screenshots — Claude cannot create image files.** Do not save or generate images. Instead, while writing:

1. Write the article with placeholder references using the exact filename you intend: `![Alt text](./img/<subsection>/suggested-name.png)` (kebab-case, English).
2. For each one, tell the user **what to capture** and the **exact path to save it** (e.g. `docs/user-guide/img/scenarios/scenario-manager-save.png`).
3. Once the user places the files, the references resolve automatically — no further edits.

**Scope & safety**

- Only document Pyplan functionality **as described by the user** — do not invent undocumented details.
- Do **not** modify config files (`docusaurus.config.ts`, `sidebars.ts`, `package.json`) unless the user explicitly asks.

**Git workflow for docs changes**

- **Never create or modify files while on `main`.** First check `git branch --show-current`:
  - On `main`: `git pull`, then create `docs/<short-description>` and work there.
  - On another branch: ask the user whether it's the intended branch before proceeding.
- Confirm the plan (files, image folder, branch) and show the written result for approval before committing.
- Commit messages follow `docs: <what changed>`.
- **Never push to `main` directly.** Push and open a PR only after the user's explicit confirmation.

## Deployment & search

- Auto-deploys to **GitHub Pages** on push to `main`; custom domain `docs.pyplan.com` is preserved via `static/CNAME`. Do not remove that file.
- Search is **Algolia DocSearch** (config + public keys in `docusaurus.config.ts`, including the "Ask AI" feature). The keys committed there are intentionally public.
